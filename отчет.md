# Отчёт по практической №1 — Lakehouse

В рамках работы развёрнут локальный Lakehouse в Docker, построены слои Bronze → Silver → Gold и проведено сравнение форматов хранения на запросе TPC-H Q3. Отчёт оформлен по форме лабораторной работы. Время и идентификаторы запросов в логах указаны в UTC; локальный часовой пояс — Europe/Moscow.

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Дорогов Дмитрий Алексеевич |
| Вариант (запрос) | Вариант 1, TPC-H Q3 — Shipping Priority |
| Масштаб `sfN` | sf5 — основной масштаб; sf1 — предварительные тесты и демонстрации Iceberg |
| Почему выбрал такой масштаб | Для customer, orders и lineitem выбран единый масштаб sf5: 0.866–0.969 ГиБ файлов на конфигурацию позволяют сохранить все повторы и резерв 22 ГиБ на диске. При предварительной проверке sf10 запрос Q3 достиг лимита памяти Trino 1,84 ГиБ. Поэтому основное сравнение выполнено на sf5. |

С учётом ограничений локального стенда выбран объём менее 50 ГБ. Фактические размеры файлов приведены ниже. Исходные данные Lakehouse и история Iceberg сохранены.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| customer | custkey, mktsegment | Фильтр mktsegment='BUILDING'; JOIN с orders по custkey |
| orders | orderkey, custkey, orderdate, shippriority | orderdate < DATE '1995-03-15'; JOIN с customer/lineitem; дата и приоритет в GROUP BY и выводе |
| lineitem | orderkey, extendedprice, discount, shipdate | shipdate > DATE '1995-03-15'; JOIN с orders; SUM(extendedprice*(1-discount)); сортировка выручки и LIMIT 10 |

Для проверки использован [Q3 на sf5](sql/q3_reference_sf5.sql). В Trino TPC-H имена колонок без c_/o_/l_ префиксов. Дополнительные orderdate/orderkey в ORDER BY обеспечивают детерминированное разрешение равной выручки.

## 5. Тесты производительности

В таблице приведено сравнение **Parquet для всей Bronze sf5: customer + orders + lineitem**. Размер усреднён по трём независимым записям, время запроса — по пяти серверным измерениям Execution Q3. Клиентское время CLI учитывается отдельно.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |

| GZIP | 4894.00 мс (среднее 5 запусков) | 930.013 | Обеспечивает меньший размер файлов, но требует больше времени на запись; различия чтения оцениваются с учётом разброса. |
| ZSTD | 4972.00 мс (среднее 5 запусков) | 971.556 | Быстрая запись и небольшой объём; выбран для конвейера как компромисс. |

¹ Сумма файлов трёх таблиц в каждом повторе, затем среднее по трём повторам. ² Время записи — wall вокруг Docker CLI через Python monotonic; суммируются три CTAS одного повтора, затем рассчитываются mean/min/max. Это не чистое серверное время записи. Выполнено 36 успешных CTAS в 12 новых схемах и 20 EXPLAIN ANALYZE Q3. Последняя запись ORC/GZIP завершилась по task timeout без создания таблицы; повторно выполнена только эта операция, 35 успешных измерений сохранены. Между частями серии был перерыв, поэтому эксперимент не был полностью непрерывным.

Проведена сверка числа строк, сумм ключей и контрольных сумм всех колонок между 12 копиями каждой таблицы; все 12 результатов Q3 совпали с эталоном. Чтение измерялось на первой копии каждого формата/кодека с циклическим сдвигом порядка запусков. Пять прогонов не дают идеального баланса по четырём конфигурациям. В CSV сохранены Planning, Execution, CPU по фрагментам, physical input в исходных единицах Trino, splits и CLI wall. Полные планы доступны по путям в поле log_file.

Минимальный размер: PARQUET+GZIP; минимальное среднее записи: PARQUET+ZSTD; минимальное среднее Execution: ORC+ZSTD. Поздние записи выполнялись дольше первых. Частоты CPU, температура и файловый кэш ОС не контролировались. Поэтому средние значения рассматриваются вместе с разбросом; перенос результатов на другой масштаб или оборудование требует дополнительных измерений.

Среда: Apple M4, 10 CPU, 16 ГиБ RAM, macOS 15.5; Docker Engine 28.4.0, Compose 2.39.4; Docker VM 10 CPU и 8 218 034 176 байт RAM. Данные: [writes](results/sf5/writes.csv), [checksums](results/sf5/checksums.csv), [reads](results/sf5/reads.csv), [summary](results/sf5/benchmark_summary.csv), [SQL матрицы](sql/benchmark_sf5.sql). | Пример скрипта восстановления данных из снапшота (time travel) | Снапшот 3588371785330260403 содержит 100 строк, текущая копия — 101. Через CTAS ... ## 7. Выводы

В работе реализовано разделение исходных данных, бизнес-преобразований и итоговой витрины по слоям Medallion. На sf5 корректность всех копий подтверждена контрольными суммами и полной сверкой десяти заказов Q3. PARQUET+GZIP дал минимальный объём, а PARQUET+ZSTD — минимальное среднее время записи, поэтому для слоёв выбран Parquet+ZSTD как компромисс между размером и скоростью. Опыты с кэшированием и компактизацией показали, что уменьшение числа файлов или объёма метаданных само по себе не гарантирует ускорения запроса. Полученные результаты относятся к локальному стенду и масштабу sf5, оцениваются с учётом разброса измерений и могут быть повторно проверены на сохранённых исходных данных.
